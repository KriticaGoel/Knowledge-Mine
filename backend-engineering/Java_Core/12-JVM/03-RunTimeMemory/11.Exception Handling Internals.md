## Why Do We Need Exceptions?

without Exception

```
int result = divide(10, 0);

if(result == -1){
    // Handle error
}
```

Caller need to add check to handle the error

This lead to:
1. Mixing of business logic and error handling code
2. Easy to forget the check
3. Bug Propagate silently
4. Code becomes difficult to maintain.

Java introduce exception to separate normal execution from error handling.

## What is an Exception?

An exception is an object that represent abnormal condition during program execution.

```
try{
int result = divide(10, 0);

}catch(Exception ex){
throw new ArithmeticException("divide by 0");}
```

## Exception Hierarchy

```
                 Object
                    │
              Throwable (only subclasses of Throwable use with throw)
              /       \
             /         \
         Error      Exception
                        │
          ┌─────────────┴─────────────┐
          │                           │
 RuntimeException             Checked Exceptions

```

1. Object -> In java everything inherit from Object

Object ob1=new ArtithmeticException();

2. Throwable -> this is a root class of anything that can be thrown by JVM or code.

Only subclasses of Throwable can use with throw.

throw new Object() // ❌ Compile-time 

3. Error -> These generally indicate serious problems that applications are not expected to recover from.
```
OutOfMemoryError
StackOverflowError
VirtualMachineError
NoClassDefFoundError
```
Normally, you don't catch these to continue normal execution.

4. Exception -> These represent conditions that applications may handle.
```
IOException
SQLException
ClassNotFoundException
ArithmeticException
NullPointerException
```
5. RuntimeException -> These usually indicate programming mistakes or invalid use of an API.

The compiler does not force you to catch or declare them.
```
ArithmeticException
NullPointerException
ArrayIndexOutOfBoundsException
IllegalArgumentException
```
6. CheckedException -> The compiler requires you to either:

Catch them, or

Declare them with throws    
```
IOException
SQLException
ClassNotFoundException
FileNotFoundException

```

## What Happens Inside JVM When an Exception Occurs?

```
public class Demo {

    static void method2() {
        int result = 10 / 0;
    }

    static void method1() {
        method2();
    }

    public static void main(String[] args) {
        method1();
    }
}
```

### Step 1 — Class Loading (Already Covered)

Before main() starts:

Demo.class is loaded.

Bytecode is verified.

Class metadata is stored in Metaspace.

The main method is identified as the entry point.

Memory:
```
Metaspace
------------------------
Demo Class
method1()
method2()
main()
```

### Step 2 — main() Frame is Created

The JVM creates a stack frame for main().
```
Java Stack

┌────────────────────┐
│ main() Frame       │
│ Local Variables    │
│ Operand Stack      │
│ Return Address     │
└────────────────────┘

```

### Step 3 — main() Calls method1()

The JVM pushes another frame.

```
Java Stack

┌────────────────────┐
│ method1()          │
├────────────────────┤
│ main()             │
└────────────────────┘

```

### Step 4 — method1() Calls method2()

```
Java Stack

┌────────────────────┐
│ method2()          │
├────────────────────┤
│ method1()          │
├────────────────────┤
│ main()             │
└────────────────────┘
```

The PC Register now points to the next bytecode instruction inside method2().

### Step 5 — Bytecode Execution

Suppose the bytecode looks conceptually like this:
```
iconst_10
iconst_0
idiv
istore_0
return
```
The Execution Engine executes instructions one by one.

iconst_10

Pushes 10 onto the operand stack.
```
Operand Stack

10
```

iconst_0

Pushes 0.
```
Operand Stack

0
10
```

idiv

The idiv instruction pops two integers:
```
0
10
```
and attempts:
```
10 / 0
```

### Step 6 — JVM Detects an Illegal Operation

The idiv bytecode specification says:

If the divisor is zero, throw an ArithmeticException.

The JVM does not return -1.

It does not return null.

Instead, it creates an exception object.

### Step 7 — Exception Object Creation

A new object is allocated in the Heap.
```
Heap

┌────────────────────────────┐
│ ArithmeticException        │
├────────────────────────────┤
│ message = "/ by zero"      │
│ cause = null               │
│ stackTrace = ?             │
└────────────────────────────┘
```

Important

This is an ordinary Java object.

It has:

* Object header
* Class pointer
* Fields
* References

### Step 8 — Stack Trace Capture

The stack trace is captured when the exception object is created. 
so that when if real stack disappears the exception object still remembers the exception and stack info

The JVM walks the current Java stack:
```
method2()
method1()
main()
```
and stores a snapshot inside the exception object.
```
Heap

ArithmeticException

message = "/ by zero"

stackTrace

↓

method2()

method1()

main()
``` 

## Why JVM need stack trace?

Imagine the current stack
```
Java Stack

┌─────────────────────┐
│ method2()           │  ← Exception occurs here
├─────────────────────┤
│ method1()           │
├─────────────────────┤
│ main()              │
└─────────────────────┘
```
Now 10 / 0 executes.

The JVM creates:
```
ArithmeticException
```
Suppose the JVM doesn't store the stack trace immediately.

What happens next?

JVM starts searching for a catch block

There is no catch inside method2().

So JVM removes (pops) method2().
```
Java Stack

┌─────────────────────┐
│ method1()           │
├─────────────────────┤
│ main()              │
└─────────────────────┘
```
Still no catch.

JVM pops method1().
```
Java Stack

┌─────────────────────┐
│ main()              │
└─────────────────────┘
```
Still no catch.

JVM pops main().
```
Java Stack

(empty)
```
Now imagine after all this, the JVM says:

"Okay, let me print where the exception happened."

Problem

The stack is already empty.

The JVM has lost all the information.

It no longer knows:

* Which method caused the exception
* Who called it
* Who called that method

Everything has already been removed.

That's why stack trace is needed and The JVM first copies the stack information in Heap memory.

### Step 9 — Exception Table Lookup

Every compiled Java method contains an Exception Table in its bytecode.

Conceptually:
```
method2()

Exception Table

From   To    Target   Type

0       15    25      ArithmeticException
```
The JVM checks:

> "Does the current method have a matching catch block?"

If yes, it jumps to the target instruction.

If no, it begins stack unwinding.

Detail:

Consider the code:

```
static void method2() {

    try {
        int x = 10 / 0;
    }
    catch(ArithmeticException e) {
        System.out.println("Handled");
    }

}
```

The compiler converts it into Bytecode something like this
```
Conceptually:

Instruction 0

load 10

Instruction 1

load 0

Instruction 2

idiv

Instruction 3

store x

Instruction 4

goto end

Instruction 5

catch block starts

Instruction 6

println

Instruction 7

return
```

When idiv fails... (10/0)

How does the JVM know

"Go to instruction 5." (catch block starts)

Where is that information stored?

The compiler creates another structure

called the Exception Table.

Think of it as a map.
```
Exception Table

Start    End    Catch At    Type

0        4        5      ArithmeticException
```
Meaning:
```
If an ArithmeticException occurs
between instruction 0 and instruction 4
jump to instruction 5
```

What happend internally?

when idiv throws exception, JVM immediately check am I inside protected area( here it 0,4)

It looks in exception table

```
Current Instruction -> 2
```

Exception table

```
0 → 4 (protected area)

ArithmeticException

Jump 5
```


Instruction 2 lies between 0 and 4.

Type also matches.

So JVM jumps directly to Instruction 5

which is catch(...) block.

**No stack unwinding** happens because the exception is handled in the same method.

## Stack Unwinding (The Heart of Exception Handling)

Example 1: No try-catch

Example 2: try and catch in method1.


### Example 1: No try-catch

```
public class Demo {

    static void method2() {
        int x = 10 / 0;
    }

    static void method1() {
        method2();
    }

    public static void main(String[] args) {
        method1();
    }
}
```

Initial Stack

```
Java Stack

┌─────────────────────┐
│ method2()           │ ← Currently executing
├─────────────────────┤
│ method1()           │
├─────────────────────┤
│ main()              │
└─────────────────────┘
```

The PC Register points to the idiv bytecode in method2().

#### Step 1: Exception Occurs

idiv detects division by zero.

The JVM:

1. Creates an ArithmeticException object in the heap.
2. Captures the stack trace. 
3. Checks the Exception Table of method2().

Result:
```
Exception Table = Empty
```
So method2() cannot handle it.

#### Step 2: Unwind Begins

What does "unwind" mean?

> Remove stack frames one by one until a method that can handle the exception is found.

The JVM pops the current frame.
```
Before

┌─────────────────────┐
│ method2()           │
├─────────────────────┤
│ method1()           │
├─────────────────────┤
│ main()              │
└─────────────────────┘

↓

After

┌─────────────────────┐
│ method1()           │
├─────────────────────┤
│ main()              │
└─────────────────────┘
```

The exception object is NOT destroyed.

It still exists in the heap.
```
Heap

ArithmeticException
```
The stack changes, but the heap object remains.

#### Step 3: Check method1()

Now the JVM asks:

> "Can method1() handle this exception?"

It checks method1()'s Exception Table.

> Empty

No handler.

So it pops method1().
```
┌─────────────────────┐
│ main()              │
└─────────────────────┘
```

#### Step 4: Check main()

Again:
```
Exception Table

Empty
```
No handler.

Pop main().
```
Java Stack

(empty)

```

#### Step 5: Nobody Handled It

At this point:
```
Java Stack = Empty
Exception object = Still in Heap
```
Since no method handled the exception, the JVM's default exception handler prints:
```
Exception in thread "main"
java.lang.ArithmeticException: / by zero
```
using the stack trace stored earlier.

Then the program terminates.

### Example 2: try-catch in method1()

```
static void method1() {
    try {
        method2();
    } catch (ArithmeticException e) {
        System.out.println("Handled");
    }
}
```


Initial Stack

```
Java Stack

┌─────────────────────┐
│ method2()           │ ← Currently executing
├─────────────────────┤
│ method1()           │
├─────────────────────┤
│ main()              │
└─────────────────────┘
```

#### Step 1: Exception Occurs

idiv detects division by zero.

The JVM:

1. Creates an ArithmeticException object in the heap.
2. Captures the stack trace.
3. Checks the Exception Table of method2().

Result:
```
Exception Table = Empty
```
So method2() cannot handle it.

#### Step 2: Unwind Begins

The JVM pops the current frame.
```
Before

┌─────────────────────┐
│ method2()           │
├─────────────────────┤
│ method1()           │
├─────────────────────┤
│ main()              │
└─────────────────────┘

↓

After

┌─────────────────────┐
│ method1()           │
├─────────────────────┤
│ main()              │
└─────────────────────┘
```

The exception object is NOT destroyed.

It still exists in the heap.
```
Heap

ArithmeticException
```
The stack changes, but the heap object remains.

#### Step 3: Check method1()

Now the JVM asks:

> "Can method1() handle this exception?"

It checks method1()'s Exception Table.

This time the Exception Table contains:
```
ArithmeticException → catch block
```
So instead of popping method1(), the JVM:

1. Places a reference to the exception object into local variable e. 
2. Changes the PC Register to the first instruction of the catch block. 
3. Continues execution.

The stack now looks like:
```
method1()   ← executing catch block
main()
```
Notice that method1() is never removed because it successfully handled the exception.

Note:

The exception object always stays in the Heap.

What changes is:

Stack frames are removed.

The JVM keeps a reference to the same exception object while searching for a handler.

When a matching catch is found, that reference is assigned to the catch parameter (e).

So there is one exception object, not a new object at each method.

## throw vs throws (Compiler + JVM Perspective)

### throw

Example:
```
static void validateAge(int age) {
 if (age < 18) {
    throw new IllegalArgumentException("Age must be 18+");
  }
}
```
#### Step-by-step
1. new IllegalArgumentException(...) creates an object in the Heap. 
2. The reference to that object is on the operand stack. 
3. The athrow bytecode instruction executes. 
4. The JVM starts exception handling:
5. Looks at the current method's Exception Table. 
6. If no handler is found, stack unwinding begins.

* Key Point

throw is an executable statement.

It generates the athrow bytecode instruction.

### throws

Example:
```
void readFile() throws IOException {
...
}
```

Does throws generate bytecode?

No.

throws is only metadata stored in the class file.

The JVM does not read throws to decide how to handle exceptions.

The compiler uses it to enforce checked exception rules.

## finally Internals

The JVM guarantees that the finally block executes before the method exits, whether it exits:

* Normally (return)
* Due to an exception

The compiler generates bytecode so that control flows through the finally block before leaving the method.

```
try {
    System.out.println("A");
} finally {
    System.out.println("B");
}
```

```
A
B
```

```
try {
    int x = 10 / 0;
} finally {
    System.out.println("Cleaning...");
}
```

```
Cleaning....
ArithmeticException
```

```
try {
    return 10;
} finally {
    System.out.println("Finally");
}
```

```
Finally
```

The method still returns 10, but only after executing the finally block.

```
try {
    return 10;
} finally {
    return 20;
}
```

The return in finally overrides the earlier return value. Its return 20

```
try {
    throw new RuntimeException();
} finally {
    return;
}
```

The exception is lost because finally forces the method to return.

Rule: Never write return inside finally.

## Try-with-Resources

```
try (BufferedReader br = new BufferedReader(...)) {
    System.out.println(br.readLine());
}
```

The compiler rewrites it into code similar to:
```
BufferedReader br = new BufferedReader(...);
try {
System.out.println(br.readLine());
} finally {
if (br != null) {
br.close();
}
}
```
So try-with-resources is mainly **compiler-generated code** that ensures close() is called, even if an exception occurs.

## Why Are Exceptions Expensive?

Creating an exception involves:

1. Allocating a new object in the heap.
2. Capturing the current call stack.
3. Filling the stack trace.
4. Possibly unwinding multiple stack frames.
5. Jumping through exception handlers.

Compared to a normal if check, this is much more work.

## Chained Exceptions

The cause field links exceptions together.

This helps you understand the original reason for a failure even after wrapping it.

we wrap exceptions instead of throwing the original one:
1. To provide higher-level business context.
2. To avoid exposing low-level implementation details.
3. To preserve the original exception in the cause field.

Layer 1 - Database

```
class ProductRepository {

    Product findById(int id) throws SQLException {
        // Database error
        throw new SQLException("Database connection lost");
    }
}
```

Database layer knows Sql not executed since db connection lost

Layer 2 - Service

```
class ProductService {

    ProductRepository repo = new ProductRepository();

    Product getProduct(int id) {

        try {
            return repo.findById(id);
        } catch (SQLException e) {

            throw new RuntimeException(
                    "Unable to fetch product",
                    e);
        }
    }
}
```

Service layer call Database layer to run the query 
and instead of actual exception throw RunTimeException Unable to fetch product
while preserving the original exception.

heap after wrapping

```
Heap

RuntimeException
------------------------
message

Unable to fetch product

cause
 │
 ▼

SQLException
-------------------------
message

Database connection lost

```

There are two exception objects.

The RuntimeException does not copy the SQLException.

It simply stores a reference to it.

Instead oif sharing technical exception to client. Every layer converts low-level exceptions into higher-level exceptions.
This is called Exception Translation.

Cause is needed so that developer knows the actual issue. Else debug is very difficult.
