## Native Method Stack

Java is designed to be platform-independent. It cannot directly call OS-specific APIs. Instead, the JVM uses native methods written in C/C++ to interact with the operating system. Each JVM implementation provides the appropriate native code for its platform, allowing the same Java program to run unchanged on Windows, Linux, and macOS.

```
JVM (written in C++)
        │
        ├── Executes Java bytecode
        │
        └── Calls Windows/Linux APIs whenever OS services are needed

```

```
    Java
     ↓
    println()
    
     ↓
    JVM
    
     ↓
    Native C/C++ Code
    
     ↓
    Operating System
    
     ↓
    Console
```

The JVM itself is written mostly in C/C++. Some Java library methods need to interact directly with the operating system, so they call native methods.

Examples include:

* File operations
* Socket/network operations
* Creating threads
* Accessing hardware
* Memory allocation inside the JVM

These methods are declared with the native keyword.

## Why do we need Native Methods?

Java cannot directly tell the operating system:
```
"Create a thread."
"Open a file."
"Allocate OS memory."
```
Instead:
```
    Java Code
      ↓
     JVM
      ↓
   Native Method
      ↓
   Operating System
```
The native code acts as a bridge between Java and the operating system.

## What is the Native Method Stack?

Just as Java methods use the Java Stack, native methods need their own stack.
```
    Java Method
       │
       ▼
    Java Stack
    
    
    Native Method
       │
       ▼
    Native Method Stack
```
When a native method is called:

1. Java execution pauses.
2. Control switches to native code.
3. A native stack frame is created.
4. Native execution completes.
5. Control returns to Java.

Example Flow
```
Thread t = new Thread();
t.start();
```
Execution:
```
       main()
        ↓
    Thread.start()
        ↓
    native start()
        ↓
    Operating System
        ↓
    Creates new thread
        ↓
    Returns to JVM
```
Notice how execution briefly moves from the Java Stack to the Native Method Stack before returning.

## Execution Engine

```
public class Demo {
    public static void main(String[] args) {
        int x = 10;
        int y = 20;
        System.out.println(x + y);
    }
}

```

The .class file contains bytecode, not machine code.

But your CPU understands only machine code (0s and 1s).

So who translates the bytecode?

👉 The Execution Engine.

Think of the Execution Engine as the brain of the JVM. Its job is to take Java bytecode and make it executable by the CPU.

### What Does the Execution Engine Do?

It has three main responsibilities:

1. Execute Bytecode

Reads Java bytecode instruction by instruction.

Example bytecode:
```
iconst_1
iconst_2
iadd
```
It understands these JVM instructions.

2. Convert Bytecode to Machine Code

The CPU cannot execute:
```
iadd
invokevirtual
aload_0
```
The Execution Engine converts them into CPU instructions such as:
```
MOV
ADD
CALL
```
These are architecture-specific instructions (x86, ARM, etc.).

3. Optimize Execution

The JVM notices frequently executed ("hot") code and compiles it into optimized machine code so it runs much faster.

We'll study this in detail when we discuss the Interpreter vs JIT Compiler.

## Interpreter vs JIT Compiler

### Approach 1: Interpreter

The Interpreter reads one bytecode instruction at a time, translates it, executes it, then moves to the next instruction.
```
    Bytecode
       ↓
    Interpreter
       ↓
    Execute one instruction
       ↓
    Next instruction
       ↓
    Next instruction
```

#### Advantages
* Very fast startup.
* No compilation delay.
* Great for code that runs only once.

#### Disadvantage

If the same method runs 10 lakh times, the Interpreter translates it 10 lakh times.

That's inefficient.

### Approach 2: JIT (Just-In-Time) Compiler

When a method is executed many times, the JVM marks it as a hot method.
```
    Method
       ↓
    Executed again...
       ↓
    Executed again...
       ↓
    Executed thousands of times
       ↓
    🔥 Hot Method
       ↓
    JIT Compiler
       ↓
    Machine Code
```
The compiled machine code is then reused directly.

No repeated translation.


Flow Diagram

```
    Java Source (.java)
        │
        ▼
      javac
        │
        ▼
    Bytecode (.class)
        │
        ▼
    Class Loader
        │
        ▼
    Runtime Memory
        │
        ▼
    Execution Engine
   ┌───────────────┐
   │ Interpreter   │
   │ JIT Compiler  │
   └───────────────┘
        │
        ▼
    Machine Code
        │
        ▼
    Code Cache
        │
        ▼
       CPU
```

### Why need both?

* The Interpreter starts execution immediately.
* The JIT Compiler compiles only methods that are used frequently.

This gives Java both:

* Fast startup.
* High performance for long-running applications.

## Code Cache

JIT store the compiled machine code in a special memory area called the Code Cache.

```
    Bytecode (.class)
       │
       ▼
    JIT Compiler
       │
       ▼
    Machine Code
       │
       ▼
    Code Cache
```
Whenever the same hot method is called again:
```
    Method Call
      │
      ▼
    Code Cache
      │
    Found ✔
      │
      ▼
CPU executes machine code directly
```
No interpretation.

No recompilation.


The Code Cache is managed by the JVM's Code Cache Manager, which is part of the JVM runtime.

The Code Cache is managed by the JVM runtime, not by the Garbage Collector. It stores machine code generated by the JIT compiler. The JVM releases it when the process exits, invalidates obsolete compiled code during deoptimization, and manages its space if the cache becomes full.

### When code cache cleared?

1. When the JVM exits ✅

This is the most common case.
```
    Application starts
          ↓
    JIT compiles methods
          ↓
    Stores them in Code Cache
          ↓
    Application ends
          ↓
    Entire Code Cache is released
```
Since the JVM process ends, all its memory (Heap, Stack, Metaspace, Code Cache) is returned to the operating system.

2. When methods become invalid (Deoptimization)

Sometimes the JVM makes an optimization that later turns out to be incorrect.

Example:

The JVM notices:
```
shape.draw();
```
For several minutes, only Circle.draw() is called.

It optimizes assuming:
```
    shape.draw()
         ↓
    Circle.draw()
```
Later, someone creates:
```
new Rectangle();
```
Now the previous optimization is no longer valid.

The JVM:

* Invalidates the old compiled code.
* Falls back to the interpreter if necessary.
* May compile a new optimized version later.

This process is called **deoptimization**.

3. When the Code Cache becomes full

The Code Cache has a limited size.

If it fills up, the JVM can:

* Stop compiling new methods.
* Reclaim space from obsolete compiled methods.
* Continue using the interpreter for methods that can't be compiled until space is available.

## To improve startup performance, modern JDKs provide technologies such as:

* **CDS (Class Data Sharing)** – Shares preprocessed class metadata between JVMs.
* **AOT (Ahead-of-Time) Compilation** – Compiles code before the application runs.
* **GraalVM Native Image** – Produces a native executable, eliminating the need for JIT warm-up at startup.
