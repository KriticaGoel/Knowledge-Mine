## Definition
The JVM creates multiple runtime memory areas when a Java program starts.

Each memory area has a specific responsibility.

Instead of storing everything in one place, the JVM separates memory to improve:

- Performance
- Memory Management
- Thread Safety
- Garbage Collection
- Scalability


## 2. Runtime Memory Areas

+------------------------------------------------------+

## 4. Responsibilities

### Metaspace

Stores Class Metadata.

Contains

- Class Name
- Method Information
- Field Information
- Runtime Constant Pool
- Constructors
- Interfaces

Does NOT store objects.

---

### Heap

Stores

- Objects
- Arrays
- Instance Variables

Garbage Collector works mainly on Heap.

---

### Java Stack

Stores method execution information.

Contains Stack Frames.

Each Stack Frame contains

- Local Variables
- Method Parameters
- Object References
- Operand Stack
- Return Information

---

### PC Register

Stores

The address of the next bytecode instruction to execute.

One PC Register per thread.

---

### Native Method Stack

Stores execution information for Native Methods.

Example

```
System.arraycopy()

File I/O

Socket APIs
```

Implemented using JNI.

## 7. Why JVM Uses Different Memory Areas

1. Performance

Objects and local variables have different lifetimes.

---

2. Thread Safety

Each thread has its own Stack and PC Register.

No interference between threads.

---

3. Garbage Collection

GC only needs to manage Heap.

It doesn't clean Stack.

---

4. Scalability

Millions of objects can exist without affecting method execution.

## 9. Important Rules

✅ One Heap per JVM

✅ One Metaspace per JVM

✅ One Java Stack per Thread

✅ One PC Register per Thread

✅ One Native Method Stack per Thread

✅ Objects live in Heap

✅ References live in Stack

✅ Class Metadata lives in Metaspace

---

## 10. Common Misconceptions

❌ Heap stores methods.

✔ Methods belong to Class Metadata.

---

❌ Stack stores objects.

✔ Stack stores references and local variables.

---

❌ PC Register stores Java code.

✔ PC Register stores the address of the next bytecode instruction.

---

❌ Objects disappear when a method ends.

✔ Objects remain until they become unreachable.

## what goes in Metaspace?


Metaspace stores the class definition, including metadata describing:

* Field definitions (their names, types, modifiers)
* Method definitions
* Constructor definitions
* Inheritance information
* Interface information
* Annotations
* Runtime metadata

## what goes in  stack (Per Thread)?

It contains Stack Frames.

Each method call creates one Stack Frame in LIFO (Last In First Out) order.

```
Stack Frame

├── Local Variables
├── Object References
├── Primitive Variables
├── Method Parameters
├── Operand Stack
└── Return Information
```

Method Parameters
```
void print(Person p, int age)
```
Both parameters are stored in the new method's stack frame.

```
print()

p

age
```

Operand Stack

This is an internal working area used by the JVM while executing bytecode.

Example
```
int c = a + b;
```
The JVM internally performs operations using the operand stack.

Return Address / Method Information

When one method calls another,
```
main()

↓

add()
```
the JVM remembers

>"After add() finishes, continue execution in main()."

That information is stored in the stack frame.

## What goes in Heap?

Storage for every object created using new (and arrays).

HEAP

✔ Objects

✔ Arrays

✔ Collection Objects

✔ String Objects

✔ Instance Variables

✔ Nested Objects


## Object Creation Flow
```
Student s = new Student();
```

### Step 1: JVM Reads the Instruction

The Execution Engine reaches:
```
new Student();
```
The bytecode contains a new instruction.

The JVM asks: Is the Student class already loaded?

If NO
```
new Student()
↓
Class Loader
↓
Loads Student.class
↓
Verification
↓
Linking
↓
Initialization
↓
Class information stored in Metaspace
```

If YES

The JVM skips loading because the class is already in Metaspace.

### Step 2: Allocate Memory in Heap (new)

Now the JVM knows the structure of Student.
```
Suppose:

class Student {
int id;
String name;
}
```
The JVM calculates the required size and allocates memory in the Heap.
```
Heap

+----------------------+
| Student Object       |
| id   = 0             |
| name = null          |
+----------------------+
```

**The constructor has NOT run yet.**

The object exists, but all fields have default values.

### Step 3: Zero Initialization

Every object is first initialized with default values.
```
int      → 0
long     → 0L
double   → 0.0
boolean  → false
char     → '\u0000'
Object   → null
```
This guarantees that Java never exposes random memory.

### Step 4: Constructor Executes

The JVM creates the object; the constructor initializes it.

Now the JVM calls:
```
Student() {
id = 101;
name = "Kritica";
}
```

The constructor updates the object.
```
Heap

+----------------------+
| Student Object       |
| id   = 101           |
| name = ----------+
+------------------|---+
                   |
                   ▼
                "Kritica"
```
### Step 5: Reference Stored in Stack

The variable:
```
Student s
```
is **not the object**.

It is only a **reference**.
```
Java Stack

main()

+----------------------+
| s -----------+
+--------------|-------+
               |
               ▼

Heap

+----------------------+
| Student Object       |
+----------------------+

```
Final Memory Diagram
```
Metaspace
------------------------
Student.class metadata

        ▲
        │

Java Stack
------------------------
s -----------+
             |
             ▼

Heap
------------------------
Student Object
id = 101
name = "Kritica"

```

Complete Flow

```
new Student()

      │
      ▼

Class Loaded?
      │
      ├── No → Class Loader → Metaspace
      │
      └── Yes

      ▼

Allocate Heap Memory

      ▼

Default Values

      ▼

Run Constructor

      ▼

Return Reference

      ▼

Store Reference in Stack

```

Now let's execute the code step by step

### Step 1: Start the JVM

The JVM starts and creates:
```
Heap
Java Stack
PC Register
Native Method Stack
Metaspace
Code Cache
```
At this point:

No Student object exists.

### Step 2: Class Loader

The JVM reaches:
```
Student.main()
```
The Class Loader loads:
```
Student.class
```
into:
```
Metaspace
```
Now the JVM knows:
```
fields
methods
constructors
bytecode
```
### Step 3: Execution Engine

The Execution Engine starts executing the bytecode.

Initially:
```
Interpreter
```
executes each instruction.

If main() becomes a hot method later, the JIT may compile it and store the machine code in the Code Cache.

### Step 4: Java Stack

The JVM invokes:
```
main()
```
A stack frame is created.
```
Java Stack

main()
```
The PC Register points to the current bytecode instruction.

### Step 5: Execute new Student()

The Execution Engine sees:
```
new Student()
```
It checks:
```
Is Student.class loaded?
```
Yes.

### Step 6: Heap Allocation

Memory is allocated in the Heap.

Initially:
```
Student
id = 0
```
### Step 7: Instance Initialization

The field initializer runs:
```
int id = 10;
```
Now:
```
Student
id = 10
```
### Step 8: Constructor

The constructor executes:
```
System.out.println("Constructor");
```
### Step 9: Reference Stored

The reference returned by new Student() is stored in:
```
Student s
```
inside the main() stack frame.
```
Stack
------
s ─────────► Heap Object
```
### Step 10: Native Method (if needed)

When you execute:
```
System.out.println("Constructor");
```
the JVM eventually calls native code to write to the console.

Execution briefly uses the Native Method Stack, interacts with the operating system, and then returns to Java execution.
