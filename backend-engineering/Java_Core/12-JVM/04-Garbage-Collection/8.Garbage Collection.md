## What is Garbage Collection?
> Garbage Collection is the automatic process by which the JVM identifies objects that are _no longer reachable_ by the application and reclaims their heap memory.

### Practice 1
```
Student s1 = new Student();
Student s2 = new Student();

s1 = s2;
```
```
Stack                          Heap

s1 --------------|           Student Object 1
                 |
s2 --------------|---------> Student Object 2

```
Student Object 1 is eligible for GC

```
Student s1 = new Student(); // A
Student s2 = new Student(); // B
Student s3 = new Student(); // C

s1 = s2;
s2 = s3;
s3 = null;

```

```
               |   
s3 = null      |-----------> Student Object 3

```

## What are GC Roots?

Garbage Collection does not care whether one object points to another. It only cares whether there is a path from a GC Root to that object.

The JVM performs Reachability Analysis. It starts from GC Roots such as local variables on thread stacks, static variables, active threads, and JNI references. Any object that cannot be reached from these roots is considered unreachable and becomes eligible for Garbage Collection

### 1. Local variables on thread stacks
``` 
  public static void main(String[] args) {
   Student s = new Student();
   }
```
Here, s is a GC Root because it is a local variable in the stack.
```
Java Stack (GC Root)          Heap

s -------------------------> Student
```
As long as s exists, the object is reachable.

### 2. Static variables
```
   class Test {
   static Student s = new Student();
   }
```
Since s is static, it remains a GC Root while the class is loaded.

### 3. Active threads

A running thread itself is considered a GC Root. Objects referenced by that thread's stack are reachable.

### 4. JNI (Native) references

Objects referenced by native C/C++ code are also GC Roots.

### Practice 1:

```
Student s1 = new Student(); // A
Student s2 = new Student(); // B

s1.friend = s2;

s1 = null;

```

After s1 = null;, are:

Object A eligible for GC?
Object B eligible for GC?

Before s1 = null

```
GC Root (Stack)

s1 -------------> A -------------> B

s2 ------------------------------> B
```

After s1=null

```
s1 = null
s2 ---------------> B

Heap
A------->B
```
JVM is not reachable to Object A from any GC root that's why Object A is eligible for GC

Object B is NOT eligible, because s2 is still a GC Root pointing to it.

### Practice 2:

```
Student a = new Student(); // A
Student b = new Student(); // B

a.friend = b;
b.friend = a;

a = null;
```

After executing only a = null;, which objects are eligible for Garbage Collection?

Solution:

```
a   -------> Student A   -------> Student B
b   -------> Student B   -------> Student A

a = null
b   -------> Student B   -------> Student A
``` 
Since Object B and Object A both are reachable from GC root b so no object is eligible for GC.

### Why doesn't Java use Reference Counting for GC?

Java does not use reference counting because it cannot detect circular references. Instead, it uses Reachability Analysis, where the JVM starts from GC Roots and marks all reachable objects. Any object not reachable from a GC Root is eligible for garbage collection.

For example

```
class Student {
    Student friend;
}

Student s1 = new Student(); // A
Student s2 = new Student(); // B

s1.friend = s2;
s2.friend = s1;

s1 = null;
s2 = null;
```

Memory after s1= null and s2= null

```
GC Roots (Stack)

s1 = null
s2 = null


        A <--------> B
```

Notice:

* A points to B.
* B points to A.
* **No GC Root can reach either object.**

What happens with Reference Counting?
* A has 1 reference (from B).
* B has 1 reference (from A).

Reference count is not zero, so they are never deleted.

❌ Memory leak.


What does Java do instead?

Java uses Reachability Analysis.

The JVM starts from GC Roots:

Can it reach A? ❌ No

Can it reach B? ❌ No

So both A and B are considered garbage, even though they reference each other.

✅ Both objects are collected.

## Heap Structure

Heap is divided into multiple regions

```
                  JAVA HEAP

+--------------------------------------------------+
|                                                  |
|        Young Generation      |   Old Generation  |
|                              |                   |
| +---------+-----+-----+      |                   |
| |  Eden   | S0  | S1  |      |                   |
| +---------+-----+-----+      |                   |
|                              |                   |
+--------------------------------------------------+
```

Most java object have short live. They died very quickly as soon as method finished.

That's why Heap is divided into two part Young Generation and Old Generation

### Young Generation
 Short live java objects

Young generation divide into three part Eden, S0,S1

```
Young Generation

+---------+-----+-----+
|  Eden   | S0  | S1  |
+---------+-----+-----+
```

Every new object is first created in the **Eden Space**. 

Suppose application created

```
new Student();
new Employee();
new Order();
new Product();
```

Initially

```
Young Generation

+-------------------------+
| Eden                    |
| Student                 |
| Employee                |
| Order                   |
| Product                 |
+-------------------------+

S0 : Empty
S1 : Empty
```

After some time, many of these objects become unreachable.

For example:
```
Student ❌ Dead
Employee ❌ Dead
Order ✅ Alive
Product ❌ Dead
```
When Eden becomes full, the JVM performs a Minor GC.

### What happens during Minor GC?

The JVM:

Removes unreachable objects.

Copies surviving objects to a Survivor space (S0 or S1).

After GC:
```
Eden

Empty

S0

Order
```
The dead objects are gone.

Only the live object (Order) is copied.

### Object Aging

Every time an object survives a Minor GC, its age increases.
```
Example:

Created in Eden
│
▼
Age = 0

Minor GC

        ▼
S0
Age = 1

Minor GC

        ▼
S1
Age = 2

Minor GC

        ▼
S0
Age = 3
```

Objects are created with Age = 0 in Eden.

After surviving the first Minor GC, their age becomes 1.

The object keeps moving between S0 and S1.

It never stays in both.

### Why are there TWO Survivor Spaces (S0 and S1)?

The JVM uses two Survivor spaces so that during each Minor GC, all live objects can be copied into the empty Survivor space. This avoids fragmentation, simplifies memory management, and makes allocation very fast.

Example:

Instead of one Survivor space, the JVM uses two.
```
+---------+-----+-----+
|  Eden   | S0  | S1  |
+---------+-----+-----+
```
Only one Survivor space is active at a time.

Example:

Minor GC 1
```
Eden

A B C D

A dies ❌
B dies ❌
C survives ✅
D survives ✅
```
After GC:
```
Eden 
(empty)

S0

C
D

S1 is empty.
```
Minor GC 2
```
New objects:

Eden

E F G H
```
Suppose:
```
C survives
D dies
F survives
G survives
```
The JVM copies all surviving objects into the other Survivor space.
```
S1

C
F
G
```
Now Eden and S0 becomes empty.

Minor GC 3

The JVM switches again.
```
S0

C
G
```
Eden and  S1 becomes empty.

This process is called **"Copying Collection"**

Objects keep moving like this:
```
Eden
↓
S0
↓
S1
↓
S0
↓
S1
```
Each time they survive:

Their age increases.

Eventually (typically around age 15, though it can vary), they're promoted to the Old Generation.

### Old Generation 

This object has survived many GCs. It's probably long-lived, so don't keep copying it between Survivor spaces. Move it to another space called Old generation

Objects that survive multiple Minor GCs are considered long-lived. Instead of repeatedly copying them between Survivor spaces, the JVM promotes them to the Old Generation, reducing the cost of future Minor GCs.


## Minor GC vs Major GC vs Full GC

1. Minor GC

When Eden becomes full. The JVM triggers a Minor GC.

Example:
```
for (int i = 0; i < 100000; i++) {
new Student();
}
```
Thousands of objects are created.

Eventually:

Young Generation
```
+---------+-----+-----+
| Eden    | S0  | S1  |
| FULL    |     |     |
+---------+-----+-----+
```

What happens?
* Scan only the Young Generation
* Remove unreachable objects
* Copy survivors to Survivor Space
* Increase their age

Old Generation is normally not collected during a Minor GC.

Minor GC is:

✅ Frequent

✅ Fast

✅ Usually short pause

2. Major GC

Suppose many objects survive and get promoted.

Eventually:

Old Generation
```
####################
####################
####################
(FULL)
```
Now the JVM needs to clean the Old Generation.

This is called Major GC.

Major GC is:

* Less frequent
* Much slower
* More expensive

Why?

Because the Old Generation contains large, long-lived object graphs.

3. Full GC

A Full GC means the JVM performs garbage collection on the entire heap.

That includes:
```
Young Generation
+
Old Generation
```
It may also reclaim other JVM-managed memory depending on the collector and JVM implementation.


```
| GC Type  | Area Collected   | Speed   |
| -------- | ---------------- | ------- |
| Minor GC | Young Generation | Fast    |
| Major GC | Old Generation   | Slow    |
| Full GC  | Entire Heap      | Slowest |

```

```
Young Generation
----------------
Eden        : FULL
S0          : FULL
S1          : EMPTY

Old Generation
--------------
99% FULL
```

JVM performs a Full GC it attempt to free space. It is not guaranteed to succeed.

During a Minor GC, if surviving objects need to be promoted to the Old Generation but there isn't enough space available, the JVM may trigger a Full GC to reclaim memory from the Old Generation. If sufficient space is reclaimed, the promotion succeeds. Otherwise, the JVM may throw an OutOfMemoryError

## Stop-The-World (STW)

The JVM temporarily pauses all application threads.Only the Garbage Collector is allowed to run. 
This pause is called: Stop-The-World (STW)

During the pause:

❌ Your application code does not execute.

❌ No new objects are created.

❌ No references change.

✅ The GC safely analyzes and updates memory.

```
Time →

Application Threads
Running ──────────── PAUSED ─────────── Running

Garbage Collector
           GC Running
```

Why JVM pause the running applications?

If application threads continue running during Garbage Collection, they can create new objects, remove references, or modify existing object references while the GC is analyzing the heap. As a result, the GC may incorrectly identify an object as reachable or unreachable, leading to an inconsistent view of memory. To prevent this and ensure heap consistency, the JVM temporarily pauses application threads during critical phases of Garbage Collection. This pause is called Stop-The-World (STW).


Why is STW Bad?

Imagine an online shopping website.

During a 500 ms STW pause:

* Users click "Buy Now."
* No request is processed.
* Responses are delayed.

If the pause lasts several seconds:

* Users notice the application has "frozen."

That's why modern collectors (like G1, ZGC, and Shenandoah) are designed to **minimize STW pauses**, even though they cannot eliminate them completely.

## G1 GC (Garbage First Garbage Collector)

Instead of dividing the heap into one large Young and one large Old space, G1 divides the heap into many small equal-sized regions.
```
+--------------------------------------------------+
| R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 | R9 | R10 |
|--------------------------------------------------|
| R11| R12| R13| R14| R15| R16| R17| R18| R19| R20 |
+--------------------------------------------------+
```
Each region is typically 1 MB to 32 MB (depending on heap size).

The JVM still has the concepts of:
```
Young Generation
Old Generation
```
But they are now made up of regions, not one fixed contiguous memory block.

For example:

Young Regions
```
R1
R2
R3
R4
```
Old Regions
```
R5
R6
R7
R8
R9
```
Later, the JVM can change which regions belong to Young or Old.

This flexibility is one of G1's biggest advantages.

### Why is it called "Garbage First"?

Suppose:
```
Region      Garbage

R1          5%
R2          80%
R3          10%
R4          90%
R5          2%
```
Instead of scanning everything, G1 says:

> "I'll clean R4 first because it has the most garbage."

Then:

> "Next I'll clean R2."

It collects the regions that will free the most memory first.

Hence the name: Garbage First (G1).

### Why did Oracle replace Parallel GC with G1 as the default?

"Parallel GC focuses on maximizing throughput but can produce long Stop-The-World pauses on large heaps. G1 divides the heap into regions, collects the regions with the most garbage first, and aims for more predictable, shorter pause times, making it better suited for large server applications."

| Feature     | Parallel GC        | G1 GC                        |
| ----------- | ------------------ | ---------------------------- |
| Heap Layout | Fixed Young/Old    | Region-based                 |
| Pause Time  | Can be long        | More predictable and shorter |
| Best For    | Small/medium heaps | Large server applications    |
| Default     | Java 8             | Java 9+                      |
