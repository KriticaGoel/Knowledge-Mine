## String 

A String is an object of the String class.

String is not a primitive type like int, char, or boolean. It is a class in the java.lang package.

```
String name = "Kritica";
```

Here:

* name is a reference variable.
* "Kritica" is a String object.
* The reference name points to that object.
  
String is special because:

* It is a class.
* It is immutable (cannot be changed after creation).
* It has a dedicated String Pool to save memory and improve performance.

### Why are Strings immutable?

There are four main reasons:

1. String Pool
* Many variables can share the same String object.
* If one variable could modify it, all others would see the change.
* Immutability makes sharing safe.
2. Security
* Strings are used for sensitive data like:
    * Database URLs
    * Usernames/passwords
    * File paths
    * Network connections
* If Strings were mutable, malicious code could change these values after validation.
3. Thread Safety
* Immutable objects can be shared across multiple threads without synchronization.
* No thread can change the String, so there are no data races on its contents.
4. Caching
* Methods like hashCode() compute their value once and can cache it because the String never changes.
* This improves the performance of collections like HashMap.

## String Pool

```
String s1 = "Java";
String s2 = "Java";
```

One String object is created, and both s1 and s2 reference the same object.

Java checks the String Pool first.

* "Java" is not in the pool → Java creates one String object in the String Pool.
* s1 points to that object.
* When s2 = "Java" executes, Java finds "Java" already in the pool, so it reuses the same object.
* s2 also points to that same object.

Why does Java do this?

Because Strings are immutable, the same object can be safely shared. This saves memory and reduces object creation.

## ==

The == operator compares references (memory addresses), not the text inside the objects.

```
String s1 = "Java";
String s2 = "Java";

System.out.println(s1 == s2);
```

True because both s1 and s2 point to the same object in the String Pool.

```
String s1 = new String("Java");
String s2 = new String("Java");

System.out.println(s1 == s2);
```

False because s1 and s2 point to different objects in the heap, even though they contain the same text.

What happens internally?

Step 1: new String("Java")

* JVM checks the String Pool.
* "Java" is not present, so it creates one String in the String Pool.
* Then new creates another String object on the heap, copying the value "Java".
* s1 points to the heap object, not the pool object.

Step 2: new String("Java") again

* "Java" already exists in the String Pool, so no new pool object is created.
* But new always creates a new heap object.
* s2 points to this second heap object.

Memory Diagram:

```
String Pool
+---------+
| "Java"  |
+---------+

Heap
+---------+      +---------+
| "Java"  |      | "Java"  |
+---------+      +---------+
     ↑                ↑
    s1               s2
```

## equals()

```
String s1 = new String("Java");  // Heap
String s2 = "Java"; // String Pool

System.out.println(s1.equals(s2));
```

Memory map

```
String Pool
+---------+
| "Java"  |
+---------+
      ↑
     s2

Heap
+---------+
| "Java"  |
+---------+
      ↑
     s1
```

s1==s2 -> false because they point to different objects.
s1.equals(s2) -> true because the text inside both objects is the same.

| Operator   | Compares                    | Result       |
| ---------- | --------------------------- | ------------ |
| `==`       | References (memory address) | Same object? |
| `equals()` | Contents (characters)       | Same text?   |

## intern();

intern() returns the reference of the String from the String Pool and ignore Heap object reference.

What does intern() do?

intern() returns the reference to the String object in the String Pool.

If the String is already in the pool: It returns the existing pooled object.

If the String is not in the pool: It adds it to the pool and returns that pooled object's reference.


Step-by-step
```
String s1 = "Java";
```

String Pool:
```
+---------+
| "Java"  |
+---------+
↑
s1
```
Now:
```
String s2 = new String("Java").intern();
```
1. new String("Java") creates a new heap object.
2. .intern() ignores that heap object's reference and returns the pooled "Java" object.
3. s2 now points to the same pooled object as s1.

Memory:
```
String Pool
+---------+
| "Java"  |
+---------+
↑   ↑
s1  s2

Heap
+---------+
| "Java"  |  ← temporary object created by `new`
+---------+
```
Therefore:
```
System.out.println(s1 == s2);
```
prints:
```
true
```
because both s1 and s2 refer to the same object in the String Pool.

## where is the String Pool stored in JVM?
In Java 7 and later, the String Pool is stored in the Heap as a special JVM-managed area. 
In Java 6 and earlier, it was stored in PermGen (Method Area).


## String implemented internally.

```
String s = "Java";
```

* s → Reference variable stored in the Stack.
* "Java" → String object stored in the String Pool (inside the Heap).
* The String object internally points to a character array (Java 8) or byte array (Java 9+). 
* The character/byte array is stored contiguously because it is an array.
* The heap itself is not guaranteed to allocate all objects contiguously.

Starting with Java 9, Oracle optimized String storage.

Instead of:
```
private final char[] value;
```
it became approximately:
```
private final byte[] value;
private final byte coder;
```
Why?

Most Strings contain only English (Latin-1) characters. Using byte[] instead of char[] reduces memory usage by about 50% for those Strings.

Step by step

```

```
JVM looks for "Python" in the String Pool.

If it doesn't already exist, it creates it there:
```
Stack                 Heap → String Pool
+------+              +---------+
|  s   | -----------> | "Java"  |
+------+              +---------+
|

+---------------> | "Python"|
                  +---------+
```
So now:

* "Java" was not modified.
* "Python" is a separate String object.
* s is simply reassigned to "Python".
* "Java" can remain in the String Pool because the pool manages pooled strings for reuse.

## How is immutability actually enforced?

Not by final keyword
```
private final byte[] value;
```
Consider:
```
final int[] arr = {10, 20};

arr[0] = 99;
```
This is perfectly legal.

final prevents:
```
arr = new int[]{30, 40};  // ❌
```
but does not prevent:
```
arr[0] = 99;              // ✅
```
So final on the internal array/reference is not sufficient by itself to make String immutable.


String's immutability comes from the combination of design choices:

* internal state is private
* internal state cannot be directly modified by callers
* no methods modify the String's contents
* String methods return new Strings when a changed value is needed
* the internal representation is carefully protected

```
String is immutable
↓
Existing String object cannot change
↓
String operation that appears to "modify" it
↓
creates/returns a new String
↓
you must assign the returned reference if you want to use it

```

## Why StringBuilder exists

```
String s = "";

for (int i = 0; i < 5; i++) {
    s = s + i;
}
```

After all iteration, multiple String objects are created in the heap, 
and the final String is assigned to s.

```
String Pool
+-------+
|  ""   |
+-------+

Heap
+-------+
|  "0"  |
+-------+
| "01"  |
+-------+
| "012" |
+-------+
| "0123"|
+-------+
| "01234"|
+-------+
```


we can use:

```
StringBuilder sb = new StringBuilder();

for (int i = 0; i < 5; i++) {
    sb.append(i);
}

String s = sb.toString();
```

StringBuilder is mutable, so append() can modify its internal buffer rather than creating a new String for every append.

```
StringBuilder
+----------------+
| internal buffer|
+----------------+
   append()
   append()
   append()
   append()
   append()
        ↓
   toString()
        ↓
   "01234"
```

String → immutable → modification creates a new String.

StringBuilder → mutable → append() modifies the existing builder.

## String vs StringBuilder vs StringBuffer.


1. String

→ immutable

```
String s = "Hello";
s = s + " World";
s = s + " Java";
```
Because String is immutable, each concatenation creates a new String result. The old objects become eligible for GC when nothing references them.


2. StringBuilder

→ mutable + not synchronized → generally faster

```
StringBuilder sb = new StringBuilder("Hello");

sb.append(" World");
sb.append(" Java");
```

The same builder object is modified:
```
StringBuilder
+-----------------------+
| Hello World Java      |
+-----------------------+
```

3. StringBuffer
→ mutable + synchronized → generally slower than StringBuilder

```
StringBuffer sb = new StringBuffer("Hello");

sb.append(" World");
sb.append(" Java");
```

The major difference is thread safety.

|                                  | String                    | StringBuilder            | StringBuffer          |
| -------------------------------- | ------------------------- | ------------------------ | --------------------- |
| Mutable?                         | ❌                         | ✅                        | ✅                     |
| Modification creates new String? | ✅                         | ❌                        | ❌                     |
| Thread-safe?                     | Immutable → safe to share | ❌                        | ✅                     |
| Synchronization                  | —                         | No                       | Yes                   |
| Typical use                      | Fixed text                | Single-threaded building | Shared mutable buffer |



## StringBuilder Internals

### 1. StringBuilder uses a mutable internal buffer

```java
StringBuilder sb = new StringBuilder("Java");
```

Conceptually:

```text
StringBuilder object
+----------------------+
| internal buffer      |
| [J][a][v][a][ ][ ]   |
+----------------------+
```

When we call:

```java
sb.append(" Programming");
```

`StringBuilder` modifies its existing internal buffer instead of 
creating a new `String` for every `append()`.

---

## 2. StringBuilder has length and capacity

```java
StringBuilder sb = new StringBuilder(10);
```

`10` represents the **initial capacity** of the internal buffer.

It does not mean the StringBuilder currently contains 10 characters.

```text
length   = 0
capacity = 10
```

After:

```java
sb.append("Java");
```

```text
length   = 4
capacity = 10
```

### Similarity with ArrayList

```text
ArrayList                 StringBuilder
──────────────────        ──────────────────
backing array             internal buffer
size                      length
capacity                  capacity
grow when full            grow when insufficient
```

For `ArrayList`:

```java
ArrayList<Integer> list = new ArrayList<>(10);
```

```text
size     = 0
capacity = 10
```

For `StringBuilder`:

```java
StringBuilder sb = new StringBuilder(10);
```

```text
length   = 0
capacity = 10
```

---

## 3. StringBuilder automatically grows

Example:

```java
StringBuilder sb = new StringBuilder(4);

sb.append("Java");       // length = 4
sb.append("12345");      // needs 9 characters
```

The initial capacity is only 4, but `StringBuilder` does not throw an exception.

It automatically grows its internal buffer.

Conceptually:

```text
append()
   ↓
Is there enough capacity?
   ├── YES → write into existing buffer
   │
   └── NO  → create larger buffer
              ↓
           copy existing contents
```

The growth formula is roughly:

```text
newCapacity = oldCapacity × 2 + 2
```

For example:

```text
old capacity = 4

4 × 2 + 2 = 10
```

The new capacity is approximately 10, which is enough for 9 characters.

> The exact implementation can vary by JDK version, so understand the growth concept rather than memorizing only the formula.

## 4. StringBuilder vs String

### String

```java
String s = "Java";
s = s + " Programming";
```

Because `String` is immutable, the original String cannot be modified. A new String result is created.

```text
"Java"
   ↓
"Java Programming"
```

### StringBuilder

```java
StringBuilder sb = new StringBuilder("Java");
sb.append(" Programming");
```

The existing mutable buffer is modified.

```text
StringBuilder
+-------------------------+
| Java Programming        |
+-------------------------+
```

---

## 5. Why StringBuilder is useful

For repeated String modifications:

```java
StringBuilder sb = new StringBuilder();

for (int i = 0; i < 1000; i++) {
    sb.append(i);
}
```

`StringBuilder` avoids creating a separate immutable `String` result for every append.

For a single simple concatenation, modern Java compilers can optimize `+`, so do not blindly replace every `+` with `StringBuilder`.

---

## 6. `StringBuilder` vs `StringBuffer`

|                       | String     | StringBuilder     | StringBuffer          |
| --------------------- | ---------- | ----------------- | --------------------- |
| Mutable               | ❌          | ✅                 | ✅                     |
| Repeated modification | Expensive  | Efficient         | Efficient             |
| Thread-safe           | Immutable  | ❌                 | ✅                     |
| Synchronization       | —          | No                | Yes                   |
| Typical use           | Fixed text | Repeated building | Shared mutable buffer |

### Interview answer

> **For repeated String modifications in a context where thread-safe mutable access is not required, `StringBuilder` is generally preferred because it is mutable and does not incur the synchronization overhead of `StringBuffer`.**

---

## 7. `length()` vs `capacity()`

```java
StringBuilder sb = new StringBuilder(10);

sb.append("Java");

System.out.println(sb.length());    // 4
System.out.println(sb.capacity());  // 10
```

Remember:

```text
length   = characters currently stored
capacity = internal buffer capacity
```

This is very similar to the `size vs capacity` concept of `ArrayList`.

## 8. `toString()`

After finishing construction:

```java
StringBuilder sb = new StringBuilder();

sb.append("Java");
sb.append(" Programming");

String s = sb.toString();
```

`toString()` gives us a **String representation** of the contents.

```text
StringBuilder
      ↓
Java Programming
      ↓
   toString()
      ↓
String
"Java Programming"
```

The purpose is to obtain a normal immutable `String` when the building process is complete.


```
StringBuilder sb = new StringBuilder();

sb.append("Java");
sb.append(" Programming");

String s = sb.toString();

```

toString() converts/returns the contents as a String.

The resulting String is a normal String; toString() does not call intern().

It does not mean "put the String into the String Pool".

If you specifically wanted the pooled reference, you'd have to do:
```
String s = sb.toString().intern();
```

```
StringBuilder sb = new StringBuilder("Java");
String s1 = sb.toString();
String s2 = sb.toString();

System.out.println(s1 == s2);
System.out.println(s1.equals(s2));
```

```
Heap

StringBuilder
+-----------+
|   Java    |
+-----------+

String Object 1          String Object 2
+---------+              +---------+
| "Java"  |              | "Java"  |
+---------+              +---------+
    ↑                         ↑
   s1                        s2
```

Therefore:
```
s1 == s2
```
compares references → false.

While:
```
s1.equals(s2)
```
compares content → true.
