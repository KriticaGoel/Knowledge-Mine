### What is ArrayList?

All objects are stored in consecutive slots (actually, the array stores references to objects).

Because of this,

finding element number 4 is

```
Base Address

+

4 × Reference Size
```
ArrayList is not synchronized. It is not thread-safe. 
If multiple threads access an ArrayList concurrently, 
and at least one of the threads modifies the list structurally, 
it must be synchronized externally.

### why ArrayList exists?


### Why can't Java arrays grow after they are created?

A Java array has a fixed size because, when it is created, 
the JVM allocates one contiguous block of memory large enough to hold all its elements. 
Once allocated, its size cannot change. 
If we need more space later, the memory immediately after the array may already be occupied by other objects, 
so the JVM cannot extend the existing array in place. 
Instead, it must allocate a new, larger array, copy all the existing elements into it,
and discard the old array. This is exactly the strategy used internally by ArrayList.

```

### Array vs ArrayList

### Why does ArrayList use an array internally instead of a linked list

ArrayList uses an array internally because most applications require fast random access. 
Arrays store references in contiguous memory, allowing the JVM to calculate an element's address directly using the index, so get(index) is O(1).

A LinkedList, on the other hand, stores elements as nodes connected by references. 
To access the nth element, it must traverse node by node, making random access O(n).

Although LinkedList can insert or delete a known node efficiently, 
finding the insertion point usually takes O(n), 
so in real-world applications ArrayList generally performs better. 
It also uses less memory and benefits from better CPU cache locality 
because array elements are stored together.

| Operation               | ArrayList                               | LinkedList                                                                                         |
| ----------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------- |
| get(index)              | O(1)                                    | O(n)                                                                                               |
| add at end              | Amortized O(1)                          | O(1)                                                                                               |
| insert/remove in middle | O(n)                                    | O(n) to reach the position, then O(1) to relink                                                    |
| Memory                  | Lower (stores references in an array)   | Higher (each node stores data + next + previous references in Java's doubly linked implementation) |
| CPU Cache               | Better locality due to contiguous array | Poor locality because nodes are scattered                                                          |

### Lazy allocation saves memory.

#### Constructor - new ArrayList<>();

Modern JDKs delay allocation. The internal array starts as a shared empty array, and the first add() triggers allocation of the default capacity (10).

#### new ArrayList<>(100);

Immediately creates an internal array capable of holding 100 elements.

No resizing until you exceed 100 elements.

Useful when you already know approximately how many elements you'll store.

#### new ArrayList<>(collection);
Copies all elements from the given collection into its own internal array.

The new ArrayList does not share the same backing array with the source collection.

## Operations of arrayList

### add()

Internally add operation checks if the backing array has enough capacity to accommodate the new element. If it does, the element is added at the next available index, and the size is incremented. If not, the backing array is resized (typically 1.5 times its current capacity), and all existing elements are copied to the new array before adding the new element.


```
capacity = 10

size = 3
```
Adding an element at the end of the list is straightforward. The new element is placed in the next available slot, and size is incremented.
```
capacity = 10

size = 10
```
Adding an element when the list is full requires resizing. The internal array is replaced with a new, larger array (typically 1.5 times the old capacity), and all existing elements are copied over.

#### why 1.5x?

The 1.5x growth factor is a balance between memory efficiency and performance. 
It reduces the frequency of resizing operations, which are expensive, while keeping memory usage relatively low. 
This factor is chosen based on empirical analysis and trade-offs between these two considerations.

old capacity = 10

new capacity = 10 + (10 >> 1) = 15 or 10 + 10/2 = 15

old capacity = 15

new capacity = 15 + (15 >> 1) = 22 or 15 + 15/2 = 22


#### why not 2x?

Doubling the capacity (2x growth) would lead to more unused memory, especially if the list doesn't grow to fill that space. 
The 1.5x growth factor is a compromise that balances the need for fewer resizes with the desire to avoid excessive memory consumption.

### get()

Retrieves the element at the specified index. Since ArrayList uses an array internally, 
this operation is very fast (O(1)) as it directly accesses the element at the given position in the array.

```

```
Internally:
```

↓

```
That's it.

Because arrays support direct indexing.

Time complexity:

```

### remove()

Removes the element at the specified index from the list. Since ArrayList uses an array internally, this operation requires shifting all subsequent elements one position to the left to fill the gap.

Suppose
```
[A][B][C][D][E]
```
Remove
```
C
```
Result should become
```
[A][B][D][E]
```
What happened?

Everything after C shifts left by one position.

Internally, ArrayList uses:
```
System.arraycopy()
```
which is a highly optimized native method.

Time complexity:
```
O(n)
```
because elements must be shifted.

### modCount (Fail-Fast Iterator)

The `modCount` field is used to implement the fail-fast behavior of ArrayList's iterator. It keeps track of the number of structural modifications made to the list. If the iterator detects that the list has been modified structurally since the iterator was created, it throws a `ConcurrentModificationException` to prevent unpredictable behavior.

While reading the list if another thread modifies the list

To detect this, ArrayList keeps a modification counter:
```
int modCount;
```
Initially
```
modCount = 0
```
Whenever the list's structure changes:
```
add()

remove()

clear()
```
Java increments it.

```
add(A)

modCount = 1

add(B)

modCount = 2

add(C)

modCount = 3
```

When the iterator is created
```
Iterator itr = list.iterator();
```
it stores
```
expectedModCount = modCount
```
Suppose
```
modCount = 5

expectedModCount = 5
```
Everything is fine.

Now another thread (or even the same thread) does
```
list.add("E");
modCount = 6
```
But the iterator still has
```
expectedModCount = 5
```
Now every time the iterator moves
```
itr.next();
```
it checks
```
expectedModCount == modCount ?
```
Which becomes
```
5 == 6 ?
```
No

Immediately Java throws
```
ConcurrentModificationException
```
#### Why is it called "Fail Fast"?

Because Java doesn't silently continue with inconsistent data.

It says:

"Something modified this list while you were iterating. I refuse to continue."

It fails immediately instead of producing unpredictable results.


### Why is elementData marked transient?

#### What Serialization?
Serialization is the process of converting an object into a byte stream, so it can be easily saved to a file or transmitted over a network. When an object is serialized, all of its fields are converted into a format that can be stored or transmitted.

```
class Employee implements Serializable {
    int id = 101;
    String name = "Kritica";
}
```

Suppose you create:
```
Employee emp = new Employee();
```
In RAM, it looks like:
```
Employee Object

id = 101
name = "Kritica"
```
Serialization converts this object's state into a stream of bytes.
```
Employee Object
│
▼
Byte Stream
│
▼
File / Database / Network
```
Notice:

✅ The object's data is serialized.

Real world example:

Serialization is like packing the object so it can be stored or transferred.

Deserialization is unpacking the box to recreate the object.


#### Why transient Matters

Suppose an ArrayList has:
```
Capacity = 1000
Size = 5
```
Internally:
```
[A][B][C][D][E][ ][ ][ ][ ] ... 995 empty slots
```
If Java serialized the entire internal array, it would save all 1000 slots, even though only 5 contain useful data.

That's wasteful.

By marking elementData as transient and implementing custom writeObject/readObject, 
ArrayList serializes only the meaningful data. That means,
ArrayList writes only the first size elements during serialization.


#### If an ArrayList has a capacity of 1000 but a size of only 5, how many elements should be serialized, and why?

Only the 5 actual elements are serialized because the internal backing array (elementData) is marked as transient. This prevents Java's default serialization from writing the entire array, including hundreds of unused slots. Instead, ArrayList implements custom serialization logic to serialize only the size number of elements, making serialization more memory efficient.


Suppose we have:
```
ArrayList<String> list = new ArrayList<>();
```
Internally:
```
Capacity = 1000
Size = 5
```
elementData
```
[A][B][C][D][E][ ][ ][ ]........995 empty slots
```
Now Java wants to serialize the object.

If elementData were not transient:

Java would serialize all 1000 array slots.
```
A
B
C
D
E
null
null
null
...
995 nulls
```
Huge waste.

So what did the JDK engineers do?

They marked only the backing array as:
```
transient Object[] elementData;
```
This tells Java:
```
"Don't use default serialization for this field."
```
Then ArrayList has its own custom serialization code that says:
```
"Instead of serializing the entire backing array, serialize only the first size elements."
```
So if:
```

Size = 5
```
Only:
```

B
C
D
E
```
are serialized.


#### why elementData is declared as transient Object[] elementData not E[] elementData?

ArrayList stores elements in an Object[] because Java generics use type erasure( removing type information at runtime ). 
At runtime, the type parameter E is no longer available, so the JDK cannot create an array of type E[]. 
Instead, it stores all elements in an Object[]. 
The compiler ensures type safety by inserting the required casts when elements are retrieved.
