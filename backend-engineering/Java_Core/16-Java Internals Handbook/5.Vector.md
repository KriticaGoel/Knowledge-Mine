Vector provides synchronized access to its legacy methods, but it is a legacy collection. For new code, we generally prefer modern collection/concurrency approaches based on the actual thread-safety requirement.
```
Vector
├── Legacy
├── Dynamic backing array
├── Synchronized legacy methods
├── O(1) get(index)
├── O(n) middle insertion/removal
└── Usually prefer ArrayList / modern concurrency tools
```

## ArrayList vs Vector

| Features            | ArrayList        | Vector                   |
|---------------------| ---------------- | ------------------------ |
| Backing structure   | Dynamic array    | Dynamic array            |
| Random access       | O(1)             | O(1)                     |
| Dynamic resizing    | Yes              | Yes                      |
| Thread-safe methods | ❌                | ✅ synchronized           |
| Performance         | Generally faster | Synchronization overhead |
| Modern choice       | **Yes**          | Usually no               |
| Legacy              | No               | **Yes**                  |

If capacityIncrement is not specified in vector, the 
default behavior is to double the size of the backing array 
when it runs out of space.

### why don't we use Vector everywhere

Because synchronization has a cost, and making every individual method synchronized 
doesn't automatically make a whole application-level operation atomic.

## capacityIncrement

Vector has a configurable: capacityIncrement

If that is positive, Vector can grow by that amount.

Otherwise, historically it can double its capacity.

So:
```
ArrayList
10 → 15 → 22 → ...

Vector
10 → 20 → 40 → ...
```
unless a capacityIncrement is specified.
