* add at the rear

## ArrayDeque → Resizable-array implementation of the Deque interface

ArrayDeque is a resizable array-backed implementation of the Deque interface.
```
Deque<Integer> deque = new ArrayDeque<>();
```
Deque means: Double Ended Queue

It allows insertion and removal from both ends.
```
             FRONT                 REAR
               ↓                     ↓
             [10] [20] [30]
               ↑                     ↑
          add/remove            add/remove
```

## Why was ArrayDeque created?

We often need a data structure where we can efficiently:

* Add at front
* Add at rear
* Remove from front
* Remove from rear

A normal ArrayList is not ideal because removing/inserting at the beginning requires shifting elements.

ArrayDeque solves this using an **array-backed circular-buffer design**.

## Internal Data Structure 

ArrayDeque uses:

> Resizable array + circular-buffer design

Conceptually:
```
[0] [1] [2] [3] [4] [5]
↑                   ↑
front               rear
```
The logical positions can wrap around:
```
0 → 1 → 2 → 3 → 4 → 5
↑                   ↓
└───────────────────┘
```

> The memory is still a linear array. It is called circular because the logical front/rear positions wrap around.

## Why Circular?

Suppose:
```
[ ][ ][10][20][30][ ][ ]
↑         ↑
front      rear
```
If we remove 10, we don't need to shift 20 and 30.

Instead, the logical front moves:
```
[ ][ ][ ][20][30][ ][ ]
↑     ↑
front  rear
```
This avoids unnecessary shifting.

## Main Operations

 Add
```
addFirst(x);
addLast(x);
   
addFirst() → FRONT
addLast()  → REAR
```
Remove
```
removeFirst();
removeLast();

removeFirst() → FRONT
removeLast()  → REAR
```
Safe/non-exception versions
```
offerFirst(x);
offerLast(x);

pollFirst();
pollLast();
```
Examine without removing
```
peekFirst();
peekLast();
```

## Method Family 
Remember this pattern:
```
             Exception        Safe/Special
Add             add              offer
Remove          remove           poll
Examine         get              peek
```
For Deque:

```
| Operation      | First           | Last           |
| -------------- | --------------- | -------------- |
| Add            | `addFirst()`    | `addLast()`    |
| Add safely     | `offerFirst()`  | `offerLast()`  |
| Remove         | `removeFirst()` | `removeLast()` |
| Remove safely  | `pollFirst()`   | `pollLast()`   |
| Examine        | `getFirst()`    | `getLast()`    |
| Examine safely | `peekFirst()`   | `peekLast()`   |

```

## Example

```
Deque<Integer> deque = new ArrayDeque<>();

deque.addLast(10);
deque.addLast(20);
deque.addLast(30);
```
Deque:
```
FRONT             REAR
↓                  ↓
[10] [20] [30]
```
Now:
```
deque.addFirst(5);
```
Result:
```
[5] [10] [20] [30]
↑                  ↑
FRONT              REAR
```
Then:
```
deque.pollLast();
```
returns:
```
30
```
Remaining:
```
[5] [10] [20]
```

## ArrayDeque as a Queue

A Queue follows:

> FIFO — First In, First Out

Use:
```
Deque<Integer> queue = new ArrayDeque<>();

queue.offerLast(10);
queue.offerLast(20);
queue.offerLast(30);

queue.pollFirst(); // 10
```
Conceptually:
```
10 → 20 → 30
↑
removed first
```

## ArrayDeque as a Stack 

A Stack follows:

> LIFO — Last In, First Out

Modern Java generally prefers:
```
Deque<Integer> stack = new ArrayDeque<>();
```
instead of legacy:
```
Stack<Integer> stack = new Stack<>();
```
Example:
```
stack.push(10);
stack.push(20);
stack.push(30);

stack.pop(); // 30
```
```
TOP
↓
[30]
[20]
[10]
```
Why?

Stack is a **legacy class** that extends Vector.

For normal stack usage:
```
Stack
  ↓
Legacy

Deque + ArrayDeque
  ↓
Modern preferred approach
```

## Time Complexity 

| Operation       |         Complexity |
| --------------- | -----------------: |
| `addFirst()`    | **O(1) amortized** |
| `addLast()`     | **O(1) amortized** |
| `offerFirst()`  | **O(1) amortized** |
| `offerLast()`   | **O(1) amortized** |
| `removeFirst()` |           **O(1)** |
| `removeLast()`  |           **O(1)** |
| `pollFirst()`   |           **O(1)** |
| `pollLast()`    |           **O(1)** |
| `peekFirst()`   |           **O(1)** |
| `peekLast()`    |           **O(1)** |
   


### Why amortized O(1) for add?

Normally:
```
add
↓
place element
↓
O(1)
```
But when the backing array becomes full:
```
add
↓
resize
↓
copy/rearrange elements
↓
O(n)
```
Since resizing is occasional, the average cost over many operations is:

> O(1) amortized

## Does ArrayDeque Allow null?

❌ No.
```
Deque<Integer> deque = new ArrayDeque<>();

deque.add(null);
```
Results in:
```
NullPointerException
```
This is a common interview trap.

Comparison
```
ArrayDeque → ❌ null
LinkedList  → ✅ null
```
 
### Is ArrayDeque Thread-Safe?

❌ No.

ArrayDeque is not synchronized.

If multiple threads need to modify a deque concurrently, you need an appropriate concurrent design rather than assuming ArrayDeque provides thread safety.

### Is ArrayDeque Sorted?

❌ No.

It maintains the order in which you add/remove elements according to the operations you perform.

It is not a sorted collection.

### 15. Does ArrayDeque Support Random Access?

❌ Not through the Deque API.

You cannot do:
```
deque.get(5); // ❌
```
like:
```
arrayList.get(5); // ✅
```
Even though ArrayDeque uses an array internally, that array is an implementation detail, not an indexed-access API.

## ArrayDeque vs LinkedList 

Both implement Deque.
```
Deque<Integer> d1 = new ArrayDeque<>();
Deque<Integer> d2 = new LinkedList<>();
```
Both provide efficient operations at the ends.

But ArrayDeque is generally preferred for typical deque usage because:

ArrayDeque
```
[10][20][30][40]
```
LinkedList
```
[Node] ↔ [Node] ↔ [Node]
```
LinkedList has:

* Node objects
* Previous/next references
* More per-element memory overhead
* More pointer chasing

ArrayDeque generally provides:

* Better cache locality
* Less per-element structural overhead
* Fewer separate node allocations

Interview answer

> "ArrayDeque is generally preferred over LinkedList for deque usage because its array-based design has better cache locality and less per-element node/link overhead."

### Important Interview Traps 🔥

* Is ArrayDeque a circular linked list?

❌ No.

It's array-backed.

* Does the physical array form a circle?

❌ No.

The array remains linear in memory.

The logical positions wrap around.

* Does ArrayDeque allow null?

❌ No.


* Is ArrayDeque thread-safe?

❌ No.

* Can ArrayDeque be used as a Stack?

✅ Yes.
```
Deque<Integer> stack = new ArrayDeque<>();
```

* Can ArrayDeque be used as a Queue?

✅ Yes.

* Does ArrayDeque maintain sorted order?

❌ No.


* Does ArrayDeque provide random access like ArrayList?

❌ No.
