### Latency 
> How long does one request take?

**Example**: An order API responds in 100 ms.

_Lower latency_ is generally better. Measure p50, p95 and p99, not just the average.

p50 = 100 ms: 50% of requests completed in 100 ms or less.

p95 = 500 ms: 95% of requests completed in 500 ms or less.

p99 = 1,000 ms: 99% of requests completed in 1,000 ms or less.

**Common techniques**: Caching, indexing, connection pooling, reducing network calls

**Java / system design examples**: Redis, DB indexes, HikariCP

### Throughput
>How much work can the system handle?

Example: An order service processes 5,000 requests per second.

_Higher throughput_ is generally better, provided latency and error rates remain acceptable.

**Common techniques**: Batching, concurrency, horizontal scaling, asynchronous processing

**Java / system design examples**: Kafka, thread pools, batch inserts

### Consistency
> Do users see correct, up-to-date data?

Example: Two customers must not purchase the last available unit.

Strong consistency is important for inventory reservations, payments and order state transitions.

**Common techniques**:Transactions, locking, conditional updates, coordination

**Java / system design examples**: ACID, optimistic locking, SELECT ... FOR UPDATE

4. **Availability** — Can the system serve requests when needed?

Example: The service remains operational when one server fails.

_Higher availability means less downtime_, but it does not automatically guarantee correct responses.

**Common techniques**: Replication, redundancy, health checks, failover

**Java / system design examples**: Multiple Spring Boot instances, database replicas

5. **Performance** — How efficiently does the system behave under a given workload?

Includes latency, throughput, resource usage and behavior under load.

Performance is an umbrella concept, not a separate metric with one universal measurement.

**Common techniques**: Profiling, load testing, query optimization, resource tuning

**Java / system design examples**: JFR, JMH, JMeter, query execution plans


### Resiliency
Resiliency is the ability of a system to handle failures, limit their impact, and recover without causing a complete service outage or unacceptable data loss.

The six important resiliency patterns

1. Redundancy and failover

Run multiple instances or replicas so one component's failure doesn't take down the entire service.

Example: route traffic away from a failed application instance.

2. Circuit breaker

Temporarily stops calls to a repeatedly failing dependency, allowing it to recover and preventing wasted resources.

Example: stop repeatedly calling a failing payment service.

3. Timeouts and controlled retries

Bound how long requests wait and retry transient failures carefully, using backoff and jitter.

Warning: retries can amplify overload and duplicate side effects.

4. Bulkhead

Isolate resources so one failing dependency or workload cannot consume all the resources needed by others.

Example: separate bounded thread pools for payment and product search.

5. Durable queues and dead-letter queues

Buffer work during temporary downstream failures, retry eligible messages, and isolate messages that repeatedly fail.

Example: queue order-confirmation emails when the email provider is unavailable.

6. Backup and disaster recovery

Recover from data loss, corruption, or a major infrastructure or regional failure.

Example: restore a database from backups or fail over to another region.


### CAP theorem
> In a distributed system, you can only have two of the following three properties at the same time: Consistency, Availability, and Partition tolerance.

Two broad strategies are possible:

**CP-style choice** - Prioritize consistency

Replica B refuses or delays operations that it cannot safely complete. The system may temporarily reject some valid requests, but it avoids confirming conflicting inventory changes.

Trade-off: some requests become unavailable during the partition.

**AP-style choice** - Prioritize availability

Replica B continues accepting operations locally. It might also sell the last unit, creating conflicting inventory state that must be reconciled later.

Trade-off: the system may accept conflicting writes or return stale data.

### PACELC Theorem

PACELC stands for:

- P — If there is a network Partition
- A or C — choose Availability or Consistency
- E — Else, when there is no partition
- L or C — choose lower Latency or stronger Consistency

CAP: When replicas cannot communicate, will I sacrifice some requests or risk stale/conflicting state?
 
PACELC: Even when replicas can communicate, will I pay the latency cost of coordination to obtain stronger consistency?
